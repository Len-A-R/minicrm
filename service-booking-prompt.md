> **Версия:** 1.0  
> **Тип проекта:** Full-stack web-приложение  
> **Стек:** C# (Backend/API), JavaScript + HTML + CSS (Frontend), REST API  
> **Архитектура:** Кроссплатформенное клиент-серверное приложение

## 0. ПРАВИЛА РАБОТЫ (КРИТИЧЕСКИ ВАЖНО)

### 0.1. Этапность и атомарность
Проект разбит на **8 этапов**. Каждый этап разбит на **атомарные задачи** (неделимые единицы работы). Каждая атомарная задача должна быть реализована, протестирована и помечена как выполненная перед переходом к следующей.

### 0.2. Работа в независимых сессиях
Каждый этап может быть запущен в **новом чате/сессии** без потери контекста. Для этого:
- В начале каждого этапа выводится **«Контекстный бриф»** — сводка всего сделанного ранее (модели данных, endpoints, структуры, договоренности)
- В конце каждого этапа выводится **«Передачный пакет»** — структурированная сводка для следующей сессии

### 0.3. Система меток (ОБЯЗАТЕЛЬНА)
После выполнения и тестирования каждого этапа нейросеть ОБЯЗАНА поставить метку:

```
╔══════════════════════════════════════════════════════════════╗
║  ✅ ЭТАП [N] ЗАВЕРШЁН                                       ║
║  Дата/время: [timestamp]                                     ║
║  Задач выполнено: [X] из [Y]                                 ║
║  Тестов пройдено: [X] из [Y]                                  ║
║  Статус: [ГОТОВ К ПЕРЕДАЧЕ / ТРЕБУЕТ ИСПРАВЛЕНИЙ]           ║
╚══════════════════════════════════════════════════════════════╝
```

Если этап требует исправлений — метка ставится только после устранения всех ошибок.

### 0.4. Тестовое покрытие
**ВЕСЬ код должен быть покрыт тестами.** Минимальные требования:
- **Unit-тесты:** каждый сервисный класс, каждый метод бизнес-логики
- **Integration-тесты:** каждый API endpoint (happy path + error cases)
- **Frontend-тесты:** критичные пользовательские сценарии (выбор услуги, валидация форм, отправка заявки)
- **Coverage:** минимум 80% покрытия кода тестами

### 0.5. Неукоснительное соблюдение требований
Все пункты этого документа являются **обязательными**. Любое отклонение должно быть согласовано явно.

## 1. ОБЩЕЕ ОПИСАНИЕ ПРОЕКТА

**Название:** ServiceBooking (рабочее название)  
**Назначение:** Платформа для онлайн-бронирования услуг специалистов (салоны красоты, медицинские услуги, консультации, ремонт и т.д.)

**Роли пользователей:**
1. **Клиент** — неавторизованный/не зарегистрированный пользователь, оставляющий заявку
2. **Специалист** — авторизованный пользователь, предоставляющий услуги, управляющий заявками и расписанием
3. **Администратор** — авторизованный пользователь с полным доступом к управлению платформой, пользователями, финансами и настройками системы

## 2. КЛИЕНТСКАЯ ЧАСТЬ (Публичная веб-страница)

### 2.1. Общие требования к UI
- Адаптивный дизайн (desktop + mobile)
- Современный, чистый интерфейс
- Цветовая схема: нейтральная, профессиональная (белый/светло-серый фон, акцентный цвет для кнопок действий)
- Валидация полей в реальном времени (до отправки формы)
- **Плавность и SPA-поведение:** при переключении между шагами формы не должно быть мерцаний, перезагрузок страницы или полной перерисовки DOM. Переходы между шагами анимированы (CSS transitions, opacity/transform), состояние сохраняется в памяти.

### 2.2. Форма бронирования — пошаговая структура

#### Шаг 1: Выбор услуги
- **Выпадающий список / поисковое поле** со всеми доступными категориями услуг
- Услуги загружаются динамически через API
- Возможность поиска/фильтрации по названию

#### Шаг 2: Выбор территориального расположения
- **Выпадающий список / карта / список** с доступными локациями
- Локации фильтруются по выбранной услуге (только те, где есть специалисты, предоставляющие эту услугу)
- Отображается адрес и краткое описание локации

#### Шаг 3: Выбор специалиста
- **Список карточек специалистов** в выбранной локации
- Карточка содержит: ФИО, фото/аватар, название заведения, рейтинг (если реализован)
- Фильтрация по специалистам, предоставляющим выбранную услугу

#### Шаг 4: Выбор конкретных услуг и цены
- **Список услуг выбранного специалиста** с ценами и продолжительностью
- **Формат элемента:** галочка (checkbox) ИЛИ залипающая кнопка (toggle button)
  - Визуально выделенное состояние "выбрано" / "не выбрано"
  - Множественный выбор разрешён
  - Отображается цена каждой услуги
  - Отображается продолжительность каждой услуги
  - Итоговая сумма и общая продолжительность обновляются динамически

#### Шаг 5: Контактные данные клиента
- **Поле "Имя клиента"** (обязательное)
  - Тип: текст
  - Валидация: не пустое, минимум 2 символа, только буквы и пробелы
- **Поле "Номер телефона"** (обязательное)
  - Тип: телефон с маской ввода
  - Валидация: формат телефона (международный или локальный), не пустое

#### Шаг 6: Желаемое время приёма
- **Поле "Дата"** — date picker, минимальная дата = сегодня
- **Поле "Время"** — time picker или выпадающий список с доступными слотами
  - Доступные слоты загружаются с учётом расписания специалиста и существующих записей
  - Недоступные слоты визуально заблокированы

#### Шаг 7: Пользовательское сообщение
- **Поле "Сообщение"** (необязательное)
  - Тип: textarea
  - Placeholder: "Дополнительная информация, пожелания..."
  - Максимум 500 символов

#### Кнопка "Отправить заявку"
- **Условия активации кнопки (логика И):**
  1. Поле "Имя клиента" заполнено и валидно
  2. Поле "Номер телефона" заполнено и валидно
  3. Выбрана хотя бы одна услуга **ИЛИ** поле "Сообщение" не пустое
- До активации: кнопка визуально заблокирована (disabled, серый цвет)
- После активации: кнопка активна (акцентный цвет)
- При клике: валидация всех полей, отправка POST-запроса на API, отображение индикатора загрузки, показ результата (успех/ошибка)

### 2.3. API Endpoints (публичные, без авторизации)

```
GET  /api/v1/services              — список всех категорий услуг
GET  /api/v1/locations?serviceId={id}  — локации по услуге
GET  /api/v1/specialists?locationId={id}&serviceId={id}  — специалисты
GET  /api/v1/specialists/{id}/services  — услуги специалиста с ценами
GET  /api/v1/specialists/{id}/slots?date=YYYY-MM-DD  — доступные слоты
POST /api/v1/bookings             — создание заявки (booking request)
```

### 2.4. Модель данных заявки (BookingRequest)

```json
{
  "id": "uuid",
  "clientName": "string (required, 2-100 chars)",
  "clientPhone": "string (required, valid phone format)",
  "specialistId": "uuid (required)",
  "services": [
    {
      "serviceId": "uuid",
      "serviceName": "string",
      "price": "decimal",
      "durationMinutes": "int"
    }
  ],
  "requestedDate": "date (YYYY-MM-DD)",
  "requestedTime": "time (HH:MM)",
  "message": "string (optional, max 500)",
  "totalPrice": "decimal (calculated)",
  "totalDuration": "int (calculated, minutes)",
  "status": "New | Confirmed | Rejected | Completed",
  "createdAt": "datetime",
  "confirmedAt": "datetime (nullable)",
  "confirmedDate": "date (nullable)",
  "confirmedTime": "time (nullable)",
  "completedAt": "datetime (nullable)",
  "actualRevenue": "decimal (nullable, filled on completion)"
}
```

## 3. ЧАСТЬ СПЕЦИАЛИСТА (Личный кабинет)

### 3.1. Регистрация
- **Страница регистрации** с формой:
  - ФИО специалиста (обязательно, 2-100 символов)
  - Email (обязательно, валидный формат, уникальный)
  - Пароль (обязательно, минимум 8 символов, заглавная, строчная, цифра)
  - Подтверждение пароля (совпадение)
  - Номер телефона (обязательно)
- После регистрации: автоматический вход или переход на страницу входа
- Хеширование паролей (bcrypt/Argon2)

### 3.1a. Общие требования к UI личного кабинета и админ-панели
- **SPA-поведение (Single Page Application):** весь личный кабинет специалиста и админ-панель работают как единое страничное приложение. Переключение между разделами (Заявки → Клиенты → Календарь → Kanban → Бухгалтерия → Настройки и т.д.) происходит **без перезагрузки страницы** и **без полной перерисовки DOM**.
- **Клиентский роутинг:** URL меняется через History API (`pushState`/`replaceState`), при прямом переходе по URL открывается нужный раздел.
- **Плавные переходы:** при смене раздела используются CSS-переходы (opacity, transform: translateX) длительностью 200–300 мс. Контент нового раздела подгружается асинхронно (fetch), старый контент скрывается плавно, новый появляется плавно.
- **Отсутствие мерцаний:** никаких белых вспышек, полной очистки `<body>` или перезагрузки `<html>`. Общие элементы (sidebar, header, навигация) остаются на месте, перерисовывается только область контента (`<main>`).
- **Состояние навигации:** активный пункт меню подсвечивается мгновенно, без задержек.
- **Индикаторы загрузки:** при асинхронной загрузке данных показывается спиннер/скелетон внутри области контента, а не на весь экран.
- **Кэширование:** данные разделов кэшируются в памяти (JavaScript-объект/Map) при первой загрузке, повторный вход в раздел использует кэш (с возможностью принудительного обновления).

### 3.2. Авторизация
- **Страница входа:**
  - Email + пароль
  - Чекбокс "Запомнить меня" (опционально)
  - Ссылка "Забыли пароль?" (опционально)
- JWT-токены (access + refresh) или сессии
- Защищённые endpoints требуют валидный токен

### 3.3. Профиль специалиста
- **Страница редактирования профиля:**
  - ФИО специалиста (редактируемое)
  - Фото/аватар (загрузка изображения, превью, удаление)
  - Название заведения (текст)
  - Территориальное расположение (выбор из списка / добавление нового)
  - **Предоставляемые услуги:**
    - Таблица/список: Название услуги | Цена | Продолжительность (мин)
    - Кнопки: Добавить услугу, Редактировать, Удалить
    - Валидация: цена > 0, продолжительность > 0
  - **Время отпуска / нерабочие дни:**
    - Календарь для выбора дат
    - Список добавленных нерабочих дней
    - Возможность удалить нерабочий день

### 3.4. Заявки (Bookings)
- **Страница со списком заявок:**
  - Таблица/карточки со всеми заявками
  - **Колонки:**
    - ID заявки
    - Дата создания
    - Имя клиента
    - Телефон клиента
    - Запрошенная дата/время
    - Выбранные услуги (свернуто/развернуто)
    - Сообщение клиента
    - Статус (цветовая индикация)
    - Действия
  - **Фильтры:** по статусу, по дате, поиск по имени/телефону
  - **Сортировка:** по дате создания (новые сверху по умолчанию)

- **Действия с заявкой:**
  1. **"Ответить клиенту"** — кнопка открывает модальное окно/форму:
     - Поле для ввода ответа
     - Кнопка "Отправить" (сохраняет ответ, отправляет уведомление)
  2. **"Подтвердить бронь"** — кнопка открывает форму:
     - Поле "Дата приёма" (по умолчанию запрошенная клиентом, можно изменить)
     - Поле "Время приёма" (по умолчанию запрошенное, можно изменить)
     - Проверка на конфликты с существующими записями
     - Кнопка "Подтвердить" → статус меняется на "Confirmed"
  3. **"Отклонить"** — кнопка с подтверждением:
     - Опциональное поле причины отклонения
     - Статус меняется на "Rejected"
  4. **"Отметить выполненной"** — кнопка:
     - Поле "Фактическая сумма дохода" (по умолчанию = сумма услуг, можно скорректировать)
     - Статус меняется на "Completed"
     - Фиксируется дата/время выполнения

- **Статусы заявок (визуальная индикация):**
  - `New` — новая (синий/оранжевый)
  - `Confirmed` — подтверждена (зелёный)
  - `Rejected` — отклонена (красный)
  - `Completed` — выполнена (серый/зелёный темный)

### 3.5. Клиенты
- **Страница "Клиенты"** — автоматически формируется из заявок
- **Таблица клиентов:**
  - ФИО (из заявки)
  - Номер телефона
  - Количество заявок
  - Последняя заявка
  - Статус (выпадающий список): `VIP` | `Обычный` | `Забанен`
  - Текстовая метка/тег (редактируемое поле, например: "аллергия на латекс", "постоянный клиент")
- **Действия:**
  - Изменить статус
  - Добавить/изменить метку
  - Просмотр истории заявок клиента
- Если клиент с таким телефоном уже существует при новой заявке — заявка привязывается к существующему клиенту

### 3.6. Интерактивный календарь
- **Страница "Календарь"**:
  - Отображение в формате: месяц / неделя / день (переключатель)
  - В календаре отображаются **подтвержденные и выполненные записи** текущего специалиста
  - **Визуальное представление записи:**
    - Время начала
    - Имя клиента
    - Услуги (кратко)
    - Статус (цветовая индикация)
  - **Действия с записью (по клику):**
    - **"Удалить"** — с подтверждением, удаляет запись из календаря, статус заявки меняется на "Rejected" (или полное удаление — по договоренности)
    - **"Перенести"** — модальное окно:
      - Новая дата
      - Новое время
      - Проверка конфликтов
      - Сохранение изменений

### 3.7. Kanban-панель
- **Страница "Kanban"**:
  - Доска с колонками, соответствующими статусам заявок:
    - `New` | `Confirmed` | `Rejected` | `Completed`
  - **Фильтр по дате:** по умолчанию — сегодняшняя дата, можно изменить
  - **Карточка заявки на доске:**
    - Время (для confirmed)
    - Имя клиента
    - Услуги (кратко)
    - Телефон
  - **Drag-and-drop:** перемещение карточки между колонками меняет статус заявки
  - При перемещении в "Completed" — запрос фактической суммы дохода

### 3.8. Бухгалтерия / Отчёты
- **Страница "Бухгалтерия"**:
  - **Фильтры периода:**
    - Быстрые кнопки: Сегодня, Неделя, Месяц, Квартал, Год
    - Произвольный диапазон дат (date picker)
  - **Сводные показатели (карточки сверху):**
    - Общий доход за период
    - Количество выполненных заявок
    - Средний чек
    - Лучший день по доходу
  - **Таблица доходов:**
    - Группировка по: дате / услуге / клиенту (переключатель)
    - Колонки: Дата/Услуга/Клиент | Количество | Сумма дохода
  - **Диаграммы (обязательно):**
    1. **Круговая диаграмма (Pie Chart)** — доходы по категориям услуг
    2. **Столбчатая диаграмма (Bar Chart)** — доходы по дням/неделям/месяцам
    3. **Линейный график (Line Chart)** — динамика доходов за период
    4. **Топ-клиенты (Horizontal Bar Chart)** — доходы по клиентам
  - **Экспорт:** кнопка "Скачать CSV" / "Скачать PDF" (опционально)

### 3.9. Администрирование (Admin-панель)
Раздел доступен только пользователям с ролью `Admin`.

#### 3.9.1. Управление специалистами
- **Страница "Специалисты"**:
  - Таблица всех зарегистрированных специалистов платформы
  - **Колонки:** ID, ФИО, Email, Телефон, Название заведения, Локация, Статус аккаунта (Active / Suspended / Pending), Дата регистрации, Тарифный план
  - **Фильтры:** по статусу, по локации, поиск по имени/email/телефону
  - **Действия:**
    - Просмотр профиля специалиста (read-only копия его профиля)
    - Блокировка / разблокировка аккаунта (`IsActive` = false / true)
    - Смена тарифного плана
    - Сброс пароля (генерация временного пароля или ссылка)
    - Удаление аккаунта (soft delete с каскадной деактивацией данных)

#### 3.9.2. Управление заявками
- **Страница "Все заявки"**:
  - Таблица заявок по всем специалистам платформы
  - **Колонки:** ID, Специалист, Клиент, Телефон, Дата создания, Статус, Сумма
  - **Фильтры:** по статусу, по специалисту, по дате, поиск по клиенту
  - **Действия:** просмотр деталей, ручная смена статуса, удаление заявки

#### 3.9.3. Управление клиентами
- **Страница "Все клиенты"**:
  - Таблица клиентов по всем специалистам
  - **Колонки:** ФИО, Телефон, Специалист, Количество заявок, Статус, Метка
  - **Фильтры:** по специалисту, по статусу, поиск
  - **Действия:** просмотр истории, редактирование статуса/метки, удаление

#### 3.9.4. Управление справочниками
- **Страница "Услуги"** — глобальный справочник категорий и услуг:
  - CRUD категорий услуг
  - CRUD услуг (название, описание, категория)
  - Привязка/отвязка услуг к специалистам
- **Страница "Локации"** — глобальный справочник локаций:
  - CRUD локаций (название, адрес, описание)

## 4. ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ

### 4.1. Архитектура
- **Backend:** ASP.NET Core Web API (C#)
- **Frontend:** Vanilla JavaScript + HTML5 + CSS3, **SPA-подобная архитектура** (без фреймворков, unless explicitly agreed). Каждый из трёх frontend-модулей (client, specialist, admin) — самостоятельное одностраничное приложение с клиентским роутингом, динамической подгрузкой контента и плавными CSS-переходами между разделами.
- **База данных:** SQLite (для разработки) / PostgreSQL или SQL Server (для продакшена)
- **ORM:** Entity Framework Core
- **Аутентификация:** JWT Bearer токены
- **Валидация:** FluentValidation или Data Annotations
- **Логирование:** Serilog или встроенный ILogger
- **Документация API:** Swagger / OpenAPI

### 4.1a. Требования к frontend-архитектуре (SPA)
- **Клиентский роутер (`router.js`):**
  - Использует History API (`pushState` / `popstate`) для смены URL без перезагрузки
  - Сопоставляет путь URL с модулем страницы (route → page module)
  - При прямом заходе по URL инициализирует нужный раздел
  - Обрабатывает «не найдено» — редирект на дашборд или 404-страницу
- **Модуль страницы:** каждый раздел экспортирует объект `{ init(container), destroy(), title }`
  - `init()` — асинхронная загрузка данных, рендер HTML в контейнер, навешивание обработчиков
  - `destroy()` — очистка обработчиков, таймеров, подписок (предотвращение утечек памяти)
- **Layout и контент:**
  - Общий layout (sidebar, header, навигация) загружается единожды при старте приложения
  - Область контента (`<main id="content">`) очищается и заполняется модулем страницы
  - Переключение между модулями сопровождается CSS-анимацией (opacity 0→1, translateX)
- **Состояние и кэш (`state.js`):**
  - Глобальный store в виде plain JavaScript объекта/Map
  - Кэш загруженных данных по ключу (например, `bookings:list`, `clients:detail:{id}`)
  - Время жизни кэша: до закрытия вкладки (in-memory), принудительный сброс по кнопке «Обновить»
- **HTTP-клиент (`api.js`):**
  - Обертка над `fetch` с единой базой URL, заголовками, обработкой JWT
  - Интерцепторы: автоматическая подстановка `Authorization: Bearer <token>`
  - Обработка 401 — редирект на страницу входа
  - Централизованная обработка ошибок (toast/notification)
- **Плавность (критично):**
  - Запрещены: `location.href = ...`, `location.reload()`, `window.open(..., '_self')` для внутренней навигации
  - Запрещена полная перезапись `document.body.innerHTML`
  - Обязательны: CSS `transition` на opacity/transform при смене контента
  - Максимальное время анимации: 300 мс
  - Индикатор загрузки (спиннер/скелетон) показывается только внутри области контента
- **Адаптивность SPA:** на мобильных устройствах sidebar превращается в off-canvas меню с плавным выдвиганием (CSS transform)

  - Отдельная сущность `AuditLog` в базе данных

  - База данных: таблица `AuditLog` для структурированного аудита
  - Минимальный срок хранения: 90 дней для файлов, 1 год для аудита в БД

### 4.8. Монетизация (подписки и платежи)
- **Модель монетизации:** SaaS-подписки для специалистов (B2B)
- **Тарифные планы (SubscriptionPlan):**
  - **Free / Trial** — пробный период (14 дней), ограниченное количество заявок/услуг
  - **Base** — базовый функционал, лимит на количество заявок в месяц
  - **Pro** — расширенный функционал, безлимитные заявки, расширенные отчёты
  - **Enterprise** — кастомный брендинг, приоритетная поддержка, API-доступ
- **Биллинг:**
  - Периоды оплаты: Monthly, Quarterly, Yearly
  - Автопродление подписки (`AutoRenew`)
  - Уведомление об окончании подписки за 3 дня
  - При истечении подписки — ограничение функционала (только просмотр, без создания новых заявок)
- **Платежи:**
  - Сущность `PaymentTransaction` для учёта всех платежей
  - Статусы: Pending, Completed, Failed, Refunded
  - Интеграция с платёжной системой (заглушка/mock для MVP, структура под реальную интеграцию)
  - Webhook-обработка статуса платежа (структура endpoint'а)
- **Лимиты и квоты:**
  - Проверка лимитов при создании заявки (если превышен — отказ с сообщением о необходимости апгрейда)
  - Проверка лимитов при добавлении услуг
  - Middleware или сервис `SubscriptionQuotaService` для централизованной проверки
- **Отчёты по монетизации (для админа):**
  - MRR (Monthly Recurring Revenue)
  - ARPU (Average Revenue Per User)
  - Churn rate (отток)
  - Конверсия Trial → Paid
  - Диаграммы: динамика подписок, распределение по тарифам, выручка по периодам
